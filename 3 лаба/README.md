# Лабораторная работа № 3. Групповой чат с интерфейсом IP

## Цель и вариант

Освоить построение сетевого интерфейса взаимодействия с программой по IP.
Вариант 1: TCP-сокеты, текстовые сообщения и разделитель команд с кодом 0.

За основу взята **вторая лабораторная работа**: `PersistentGroupChat`, интерфейс
`GroupChat`, модели, схема H2 и транзакции перенесены без изменения. База данных
теперь находится только у сервера. Клиент использует `TcpGroupChatClient`, который
реализует тот же интерфейс, передавая вызовы через TCP. Можно запустить несколько
клиентов в разных процессах и на разных компьютерах.

## Архитектура

```text
Консоль Main → TcpGroupChatClient → TCP/IP → TcpGroupChatServer
                                              ↓
                                     PersistentGroupChat → H2
```

Сервер принимает соединения на заданном IP-адресе и порту. Каждое соединение
обслуживается отдельным потоком; клиенты используют одно общее потокобезопасное
хранилище. Операции с БД выполняются транзакционно, как во второй лабораторной.
При остановке сервера закрываются сокеты и обработчики, затем база данных.

## Сборка и запуск

Требуются JDK 17+ и Maven 3.9+. В терминале перейдите в папку `3 лаба`:

```shell
mvn test
mvn package
```

Запустите сервер в первом терминале:

```shell
java -jar target/tcp-group-chat-1.0-SNAPSHOT.jar server
```

По умолчанию сервер слушает `127.0.0.1:5555`, а база создаётся в
`data/group-chat.mv.db`. Для остановки нажмите Ctrl+C. Для использования существующей
базы второй лабораторной сначала остановите её программу, затем передайте путь к
базе без расширения `.mv.db`:

```shell
java -jar target/tcp-group-chat-1.0-SNAPSHOT.jar server 5555 "../2 лаба/data/group-chat"
```

Во втором и третьем терминалах запустите клиентов:

```shell
java -jar target/tcp-group-chat-1.0-SNAPSHOT.jar
```

Клиенту можно передать IP-адрес или имя хоста и порт:

```shell
java -jar target/tcp-group-chat-1.0-SNAPSHOT.jar 192.168.1.10 5555
```

Для подключений с другого компьютера сервер должен слушать доступный сетевой
интерфейс. Третий аргумент после `server` задаёт адрес привязки:

```shell
java -jar target/tcp-group-chat-1.0-SNAPSHOT.jar server 5555 data/group-chat 0.0.0.0
```

Порт должен быть доступен в локальной сети и разрешён брандмауэром.

## Протокол TCP-CHAT/1

### Формат и выделение сообщений

Все команды и ответы — текст в **UTF-8**. Один кадр содержит поля, разделённые
символом TAB (`0x09`), и завершается **одним байтом NUL (`0x00`)**. Символ новой
строки не завершает кадр. В таблицах ниже `␉` означает TAB, `␀` — NUL; это условные
обозначения, а не символы, которые нужно отправлять буквально.

Специальные символы внутри каждого поля экранируются:

| Символ в значении | Текст в кадре |
|---|---|
| Обратная косая черта | `\\` |
| TAB | `\t` |
| LF | `\n` |
| CR | `\r` |
| NUL | `\0` |

Например, значение из двух строк передаётся как `Привет\nВсем`, сохраняя перенос
строки после декодирования. Кириллица и emoji передаются непосредственно в UTF-8.
Экранирование применяется и к имени пользователя, и к тексту, и к описаниям ошибок.

Получатель читает поток до NUL, затем декодирует целый кадр. Поэтому команда может
приходить частями, включая разрыв внутри UTF-8 символа; несколько команд могут
приходить одним чтением. Никаких предположений о границах TCP-пакетов нет.
Максимальный размер кадра — 8 MiB без завершающего NUL. Неверный UTF-8,
неизвестная escape-последовательность, превышение лимита или EOF посередине кадра
закрывают данное соединение; неполная команда не исполняется.

### Вызов функций

Клиент посылает команду и ожидает один ответ. Ответы идут в порядке запросов.
В Java-клиенте одновременно выполняется один вызов на соединение; разные
соединения работают параллельно. Идентификаторы запросов при такой схеме не нужны.

| Метод `GroupChat` | Команда | Успешный ответ |
|---|---|---|
| `connect(name)` | `CONNECT␉name␀` | `OK␀` |
| `disconnect(name)` | `DISCONNECT␉name␀` | `OK␀` |
| `setNotificationsEnabled(name, enabled)` | `NOTIFY␉name␉true/false␀` | `OK␀` |
| `getUserState(name)` | `STATE␉name␀` | `OK␉name␉online␉lastConnectedAt␉notificationsEnabled␀` |
| `sendMessage(name, text)` | `SEND␉name␉text␀` | `OK␉id␉sender␉text␉sentAt␀` |
| `receiveMessages(name)` | `RECEIVE␉name␀` | `OK␉count␉message1…messageN␀` |
| `getHistory(name)` | `HISTORY␉name␀` | `OK␉count␉message1…messageN␀` |

Каждое сообщение в списке — четыре отдельных поля: `id`, `sender`, `text`,
`sentAt`. Поэтому ответ со списком содержит `2 + 4 × count` полей, включая `OK`
и `count`. Пустой список — `OK␉0␀`. Идентификаторы — положительные десятичные
числа. Время — ISO-8601 UTC, например `2026-10-06T09:00:00Z`. Логические значения
— строго `true` и `false`. Регистр команд значим.

Пример обмена (строки в примере — отдельные кадры):

```text
Клиент → CONNECT␉Анна␀
Сервер → OK␀
Клиент → SEND␉Анна␉Привет!␀
Сервер → OK␉1␉Анна␉Привет!␉2026-10-06T09:00:00Z␀
Клиент → RECEIVE␉Анна␀
Сервер → OK␉1␉1␉Анна␉Привет!␉2026-10-06T09:00:00Z␀
Клиент → RECEIVE␉Анна␀
Сервер → OK␉0␀
```

### Доставка оповещений

Используется **опрос сервера (polling)** командой `RECEIVE`. При отправке сообщения
сервер сохраняет его в истории и добавляет в постоянные входящие очереди всех
пользователей, которые находятся в сети и включили уведомления, включая отправителя.
Клиент запрашивает очередь, сервер возвращает сообщения по возрастанию номера и
удаляет их из очереди в той же транзакции. Повторный запрос возвращает только новые
сообщения. В консольной программе получение и показ оповещений выполняются пунктом
5 меню; произвольный клиент может вызывать `RECEIVE` периодически.

`NOTIFY … false` предотвращает добавление будущих сообщений в очередь пользователя.
Уже доставленные сообщения сохраняются. История доступна независимо от настройки
оповещений. `DISCONNECT` предотвращает новые доставки и отправку сообщений данным
пользователем. Очереди, история, время подключения и настройки переживают перезапуск
сервера благодаря H2.

Сетевое соединение является транспортом вызовов, а `CONNECT`/`DISCONNECT` управляют
сохранённым состоянием пользователя. Как и в прежней консольной программе, через
одно соединение можно работать с несколькими пользователями. Закрытие сокета не
заменяет `DISCONNECT` и не меняет сохранённый статус. Это учебный протокол без
авторизации пользователей и TLS.

### Ошибки и обрыв соединения

Формат ошибки: `ERR␉code␉description␀`.

| Код | Причина | Исключение Java-клиента |
|---|---|---|
| `ARGUMENT` | Неизвестная команда, неверные поля, пустой ввод, неизвестный пользователь | `IllegalArgumentException` |
| `STATE` | Например, отправка отключённым пользователем | `IllegalStateException` |
| `STORAGE` | Ошибка серверного хранилища | `ChatStorageException` |

После обычной ошибки команды соединение остаётся пригодным для следующих запросов.
Время подключения клиента ограничено 5 секундами, ожидание ответа — 10 секундами.
При ошибке ввода-вывода клиент закрывает сокет и сообщает об ошибке; автоматически
повторять команды нельзя, поскольку сервер мог уже выполнить запрос.

`RECEIVE` сохраняет семантику второй лабораторной: очередь очищается при выполнении
операции, до подтверждения получения клиентом. При обрыве связи ответ может быть
потерян; сообщение остаётся в `HISTORY`. Протокол не обещает гарантированную доставку
оповещений при сетевом сбое. Ответы истории и очереди также ограничены размером
кадра; постраничное чтение в этом варианте не реализовано.

## Проверка

```shell
mvn test
```

Сохранены 6 тестов первой и 4 теста второй лабораторной. Добавлены 11 тестов
`TcpGroupChatTest`, использующих настоящие сокеты на loopback и H2 во временном
каталоге. Порт выбирается операционной системой, рабочая база не затрагивается.

Проверяются все методы через TCP, доставка между разными клиентами, отключённые
пользователи и настройки уведомлений, очистка очереди, сохранение после перезапуска,
ошибки, кириллица/emoji/управляющие символы, фрагментация и объединение кадров,
незавершённые и некорректные кадры, лимит размера, параллельная отправка 100 сообщений
через четыре соединения и закрытие активных соединений сервером.

Для ручной проверки подключите Анну в одном клиенте, Бориса — в другом. Отправьте
сообщение от Анны и выберите получение сообщений для Бориса. Повторное получение
даст пустую очередь. Отключите уведомления Бориса, отправьте ещё одно сообщение:
его не будет в очереди, но оно будет в истории. Перезапустите сервер с той же базой
и проверьте сохранённые состояния и историю.

## Основные файлы

| Файл | Назначение |
|---|---|
| `TcpProtocol.java` | Выделение кадров, UTF-8, экранирование и модели на проводе |
| `TcpGroupChatServer.java` | TCP-сервер, диспетчер команд и обработчики клиентов |
| `TcpGroupChatClient.java` | Вызов всех методов `GroupChat` через TCP |
| `ServerMain.java` | Запуск и остановка сервера |
| `Main.java` | Консольный сетевой клиент |
| `PersistentGroupChat.java` | Хранилище из лабораторной № 2 |
| `TcpGroupChatTest.java` | Интеграционные сетевые тесты |

Каталоги сборки `target/` и рабочей базы `data/` исключены из Git.
